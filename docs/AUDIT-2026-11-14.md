## Fixed this wave

1. **Security (PR #58):** streamed HTTP bodies were fully buffered before checking
   limits; several routes trusted `Content-Length`. Now they stream with caps.
   Malformed signed webhook JSON responds with 400, not an unhandled error.
2. **Stability (PR #58):** rate-limiter regression test froze the clock on 2026-11-13
   while constructor expiry used current time. It now uses a current base.
3. **Reliability (this PR):** private and public racing used duplicated manually
   synchronized 29-car allowlists; a common shared catalog now derives IDs from
   original starter/season cars plus the purchasable shop, with a cross-layer test.
4. **Documentation (this PR):** README was describing now-replaced memory-only
   room state, per-isolate rate limits, and an older 11-car catalog.

## Useful competitive patterns (design ideas, not copied assets)

- **Monkeytype** (https://monkeytype.com/about): deep per-session typing analytics,
  consistency and error statistics; add optional detail *after* a clean race screen,
  not a dense main dashboard.
- **Nitro Type** (https://www.nitrotype.com/updates): visible vehicles, leagues,
  recurring cosmetics, seasonal events; adopt an original Mongolian visual identity,
  clear bot disclosure, and non-pay-to-win collectible rewards.

### Suggested next functional waves

1. A **30-second first-race onboarding** and one-click rematch; instrument
   first race completion and retry conversion without sending prompt keystrokes
   or personal text to analytics.
2. **Post-race analytics**: WPM trend, accuracy, pacing and mistakes, personal
   best, mobile vs desktop splits; expose opt-in details to avoid dashboard overload.
3. **Scalable real-human competitive queue**: shard matching keys by region/tier,
   keep player score/ledger writes idempotent, separate casual and official ranks.
4. **Seasonal social loops**: friend challenge links, verified team events,
   moderated weekly leagues, anti-smurf safeguards and seasonal cosmetics.
5. **Full operator readiness**: Wire refunds, privacy/export/deletion,
   abuse investigation, latency alerts, WAF and staged rollback runbooks.

## Architecture direction

```text
Browser React/Vite
  -> same-origin Hono Worker (/api/*, static files)
       -> public queue coordinator (sharded only after load data)
          -> match-specific Durable Objects for state + WebSocket resume
       -> identity + progression + paid-order event ledgers
          -> idempotent SQLite writes and provider reconciliation
```

Avoid a risky database/DO replacement until measurable load, cost, and write
consistency evidence justify it. Preserve gameplay, player receipts, season
entitlements, and original car assets during any migration.

## Second-pass reconciliation (2026-11-14; changes require exact-head CI)

The first wave fixed body limits, shared catalogs, flaky tests, and reward
eligibility; a second line-by-line audit uncovered four more cross-boundary
issues:

1. **Forged multiplayer appearance**: the WebSocket query string selected
   locked catalog cars without consulting server ownership. The private-room
   edge validated only a few paid-exclusive decorations. New policy:
   always authorize an online car/trail/title/sticker from trusted starter
   defaults, authoritative XP, earned-item records, or paid receipts.
2. **Double charging between ledgers**: a server-earned purchase and a
   paid-wallet purchase were independently idempotent but did not consult
   the other store. The next wave blocks cross-ledger duplicates and makes
   duplicate battle-pass cosmetics eligible for coin compensation.
3. **Purchased equipment not portable**: a paid item could be displayed
   from the browser wallet, but `/progression/equip` rejected it because
   it checked only earned inventory. Online equipped choices now accept
   owned paid and supporter cosmetics, including account merges.
4. **CI drift**: GitHub switched `ubuntu-latest` to Ubuntu 26.04, where
   Playwright Chromium's `--with-deps` could not find obsolete font
   packages. Both regular CI and the manual production verification
   job are pinned to compatible Ubuntu 24.04 runners. The production
   deployment action remains manual and approval-gated.

### Explicit remaining release gates

- **P0 — Real payments:** Wire merchant-signed success/refund/dispute lifecycle
  and operator reconciliation; canned response tests cannot establish this.
- **P0 — Identity/privacy:** end-to-end OAuth in actual browsers, unlinking,
  session invalidation, export/deletion policy, paid ledger retention rules.
- **P1 — Competitive integrity:** low-variance replay/macro detection, abuse
  appeal trail, verified PvP queues separated from casual bot races.
- **P1 — Capacity:** benchmark the global queue DO with 100–500 concurrent
  WebSockets; record p95 input acknowledgments, reconnect success, and
  restart recovery before considering sharded queues.
- **P1 — Operations:** health alerts, explicit payment/provider error metrics,
  retention limits, backup restore drills, and rollback runbooks.
- **P2 — Product:** optional per-second WPM consistency graph and raw WPM
  (Monkeytype pattern), controlled weekly leagues / garage goals (Nitro Type
  pattern), low-friction novice onboarding, mobile IME and VoiceOver/TalkBack QA.

Do not merge major dependency bot PRs, advertise anti-cheat certification,
or deploy production just because unit/Chromium checks pass.
